# plugin-chat-approval — 聊天审批：owner 与她的 IM 私聊作审批面

**包名**: `@aalis/plugin-chat-approval`  
**源码**: `packages/plugin-chat-approval/src/index.ts`  
**契约**: [api-approval](../api/api-approval.md)（审批面的登记与接入）

## 概述

每个（owner 的 IM 身份，机器人账号）一份接入：她经这个账号发起的审批（在与这个账号的私聊里、在群里都算），推到她与这个账号的私聊，owner 引用那条审批消息回复「同意」或「拒绝 原因」即结。她经这个账号亲手说话（私聊或群里，点没点名都算）即在场。WebUI 与终端发起的、别人的回合里的、经别的机器人账号的审批不推到这里。

只经契约组合，不认平台：owner 取权限服务的判定，一对一取适配器的声明，引用取投递结果里的平台消息 id（schema-message 的 `messageIds`）。

## 插件声明

```ts
definePlugin({
  name: '@aalis/plugin-chat-approval',
  displayName: '聊天审批',
  subsystem: 'authority',
  uses: {
    approvals,
    events,
    gateway,
    hooks,
    lifecycle,
    logger,
    authority: optional(authority),
    sessionManager: optional(sessionManager),
    platform: optional(platform),
  },
  apply: run,
});
```

- 激活时登记一个审批面，登记名 `chat`，随激活撤回。停用（`lifecycle.signal` 断开）之后不再往私聊发消息、不再等投递回执。消息发不出（网关不在、发送出错、适配器的回执出错）时记一条 warn，不抛。
- `events`：监听 `inbound:message` 记在场、建接入。
- `authority`、`sessionManager`、`platform` 任一缺席时认不出 owner 的私聊：不接入、不推，审批照旧只推给 WebUI 与终端。

## 认 owner 亲手发的消息

一条入站消息不带 `source`、发言者是 owner（权限服务的 `isOwner`，owner 的 IM 身份要登记在 `owners` 里），就是 owner 亲手发的。不带 `source` 的消息不带 `actor`（触发器不给没点名的话回填身份），这与权限服务判这一轮为 `hand` 且参与者是 owner 等价。在场、建接入与应答都用这一判定。

## 接入与在场

接入按（身份，机器人账号）记，身份是这条消息的平台与发言者，机器人账号取消息的 `selfId`。她经一个账号第一次亲手说话时建，建时定下她与这个账号的私聊：会话表里的根会话，机器人账号（`originChat.selfId`）就是这个账号，且按 api-session-manager 的 `oneToOneWith`（不给 `isOwner`）是她自己的私聊：

- 根会话的出生平台就是她这个身份的平台；
- 出生平台的适配器（与会话管理建档时判一对一用的同一个）在 `sessionTypes` 里明确声明了这个窗口的类型（`originChat.type`）为一对一。不声明会话类型的平台整个按一对一推断（api-platform 的 `sessionTypesOf`），这种推断出的一对一不算：那样的平台上群员也会被当成唯一的对端；
- 对端（`originChat.targetId`）就是她。实现端上报了机器人自己发的消息、机器人账号又登记成 owner 时，那条消息的发言者是机器人账号，它没有这样的私聊，不建接入，也就不算在场、不能应答。

建之前先等会话管理收录这条入站（`recordInbound`，与网关等的是同一次）：她第一次私聊这个账号时，私聊与这条入站同拍建档，第一条消息就能建。没有这样的私聊就不建，等她来私聊。WebUI、终端的会话没有出生平台，它们的 owner 身份不建接入。群号恰好是 owner 的 QQ 号的群是多方窗口，不会被当成她的私聊。

接入经 `attend(owner, sink, { selfId })` 限定：只覆盖这一轮的参与者里有她、且所在会话的根会话经这个账号的审批。从 WebUI 往群里或往她的私聊插话发起的，参与者是 WebUI 的身份，不推到这里。

在场：监听 `inbound:message`，她经这个账号亲手说话即对这份接入上报在场，私聊与群里说的都算，没点名、在触发相位就被吞掉的群聊也算（所以不挂在入站相位上）。之后按审批服务的规则：最近一次上报起 10 分钟内，或推给它的审批还没结，就算在场；推来的审批都结了，回到她自己的 10 分钟。本插件不另记发言时刻、不定时报离开。

## 推送

审批推到这个接入时，经网关往接入建时定下的私聊发一条宿主提示（`source: 'system'`）。不设 `markup`，正文按纯文字发，参数里的 `<at>`、`<image>` 之类逐字显示。文字进本插件字典，网关按会话的语言渲染：

```
需要你批准：exec
来源：群 20001（读书会）
命令：rm -rf build
目录：workspace:/proj
引用这条消息回复「同意」，或「拒绝」加原因；5 分钟内不回按过期。
```

每张都有来源一行：审批所在会话的根会话是群还是私聊（按 `originChat.multiParty`，本插件写的固定字）与窗口 id（`originChat.targetId`），会话名只作附注，换行与制表符换成空格、经 `sanitizeForCard` 清洗，不能另起一行；只写名字的话，群名由群管理员控制，改成「私聊」之类就能让她以为审批来自自己的会话。会话管理不在、判不出窗口时写「会话」与会话 id。

事实按审批对象的 `facts` 逐行列出命令、目录、文件、改动、参数，与 WebUI、终端收到的是同一份逐字的事实，各经 `clipForCard` 清洗并截断：每项最多 500 字，超出的保留首尾各一半、写明省略了多少字。末行的剩余分钟数按审批对象的到期时刻 `expiresAt` 算，不足一分钟的按一分钟；墙钟已过到期时刻、等待的计时器还没到时（系统休眠、改了时钟）也写一分钟。

消息没送达（投递失败、等不到回执或适配器的回执出错）时，owner 在这里看不到它：这张还在等就对这份接入上报离开，审批服务把推给它、还没结的都算没收到。WebUI 或终端在场时照常在那里等，否则按 30 秒的重连宽限结算，不白等满时限；其间她再亲手说话，接入上报在场，审批服务补推，没送达的这张重发，已经送达过的不再发（按审批 id 认）。已经结了的那张迟到的投递失败不碰在场。送达、投递结果带了平台消息 id 时，记下这些 id，认引用它的回复。

平台不给消息 id 时审批消息照发，但认不出引用它的回复，随后补一句「这条审批无法在这里应答，请到 WebUI 或终端处理。」

推到私聊的这些消息与别的宿主提示一样记成事件标记进会话历史，不进模型的上下文。

## 应答

在 `inbound:command` 相位截下。只认接入定下的私聊里她亲手发的消息（发言者与机器人账号对得上这份接入，消息的会话就是那个私聊），同时满足下面两条才处理，其余照常往下（交给指令解析与 agent）。她在群里说「同意」不截下、不回「请引用」，当普通消息进那一轮：只认引用审批消息的回复，群里没有审批消息可引用。

- 正文是应答词：超过 200 字的不算；去掉首尾的空白（含全角空格）与常见标点（`。！!.~，,？?：:`）后，整条恰为「同意」或「approve」为批准；以「拒绝」或单词「deny」开头为拒绝（「denylist」不算），后面可带原因（作为说明转给模型）。英文不分大小写，不收 y、n。尾部去掉的标点里有问号的是在问，不是应答：「同意？」「同意？！」「拒绝吗？」都不算；「同意吗」「同意不了」「先别批」之类既不是批准也不是拒绝。不是应答的，引用了审批消息也照常往下。
- 引用了这个私聊里的某条审批消息，或这个私聊有推来、还没结的审批。

审批消息 id 与去重都按这个私聊的会话 id 记。

处理：

- 按入站消息 id 去重：同一条重复到达的静默吞掉。
- 引用的是审批消息：带回审批的内容哈希应答。应答成功不另发，回合本身的回复会说明结果；这张已经结算（含在别处处理过的）回「这张已经处理过。」；其余被拒的（如审批服务不在）回「应答没有生效：」加原因。
- 没引用审批消息：不批，回「要批准或拒绝，请引用那条审批消息回复。」；推着的审批都认不出引用时（平台没给消息 id），回「这条审批无法在这里应答，请到 WebUI 或终端处理。」

处理过的消息一律吞掉：不进指令解析、不交给 agent，也就不会起新的一轮把在跑的那一轮中止。A 结算后紧接推出 B 时，引用 A 的回复只认到 A，回「这张已经处理过」，不会批 B。

照常往下的消息交给 agent。今天的 agent 按会话 latest-wins，新消息到达时中止这个会话里在跑的回合：owner 在私聊里发普通消息（包括引用了审批消息、但不是应答的）时，这个私聊里在等审批的那一轮随之中止，审批按撤销结算；群里发起的那一轮不受影响。按到达先后处理同一会话的消息由通道层负责，通道层尚未实现，落地后再改。

## 结算

只在过期时、且这张送达过这个私聊时发一行「exec 的审批已过期。」：等满时限的，与覆盖它的在场都失效、宽限内没有恢复的。在私聊里回的、在别处批准或拒绝的、撤销的不另发。

## 已知的边角

- 指令的意图确认（[plugin-commands](./plugin-commands.md)）在等时，会把这个人在这个会话里的下一条消息整条吞掉（y 为确认，其余取消）。两者同时在等、且指令插件的中间件先挂上时，回审批的那条会被当成取消意图确认，审批照旧等着。词表不收 y、n，反过来不会误吞。
- 审批消息经 IM 平台的服务器转发，命令、目录、参数与改动原样在内，群里发起的也一样。审批服务不按文字或路径猜密钥，不想让这些经平台的，不装本插件。
- 她在群里说过话、但没看私聊时，推到私聊的审批等满时限才过期。
- 记住最近 1000 条审批消息的 id（只记它是哪一张审批的消息）与 1000 条应答过的入站消息 id，更早的认不出。
