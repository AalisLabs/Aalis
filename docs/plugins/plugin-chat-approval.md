# plugin-chat-approval — 聊天审批：owner 与她的 IM 私聊作审批面

**包名**: `@aalis/plugin-chat-approval`  
**源码**: `packages/plugin-chat-approval/src/index.ts`  
**契约**: [api-approval](../api/api-approval.md)（审批面的登记与接入）

## 概述

owner 在与她的 IM 私聊里让她做要审批的事时，审批推回这个私聊，owner 引用那条审批消息回复「同意」或「拒绝 原因」即结。只推在这个私聊里发起的审批：WebUI 与终端的会话、别的私聊里的审批不推到这里。群里与别人的私聊不推：这些回合本就不能产生审批（见 api-approval 的「谁能产生审批」），审批服务在任何审批面之前直接拒绝。

只经契约组合，不认平台：owner 取权限服务的发起类别，一对一取适配器的声明，引用取投递结果里的平台消息 id（schema-message 的 `messageIds`）。

## 插件声明

```ts
definePlugin({
  name: '@aalis/plugin-chat-approval',
  displayName: '聊天审批',
  subsystem: 'authority',
  uses: {
    approvals,
    gateway,
    hooks,
    lifecycle,
    logger,
    authority: optional(authority),
    sessionManager: optional(sessionManager),
    platform: optional(platform),
  },
  apply: run,
});
```

- 激活时登记一个审批面，登记名 `chat`，随激活撤回。停用（`lifecycle.signal` 断开）之后不再往私聊发消息、不再等投递回执，到点上报离开的计时器在清理时撤掉。消息发不出（网关不在、发送出错、适配器的回执出错）时记一条 warn，不抛。
- `authority`、`sessionManager`、`platform` 任一缺席时认不出 owner 的私聊：不接入、不推，审批照旧只推给 WebUI 与终端。

## 认 owner 的私聊

一条入站消息算 owner 在与她的一对一窗口里亲手发的，要同时满足：

- 权限服务的 `originOf` 判这一轮为 `owner`，与执行守卫判发起类别同一份定义：消息不带 `source` 与 `actor`，会话的房间类别为 owner-only，发言者是 owner（owner 的 IM 身份要登记在 `owners` 里）；
- 根会话有出生平台，且就是消息的平台：WebUI 往这个私聊插话（平台是 `webui`）不算；
- 出生平台的适配器（与会话管理建档时判一对一用的同一个）在 `sessionTypes` 里明确声明了这个窗口的类型（`originChat.type`）为一对一。不声明会话类型的平台整个按一对一推断（api-platform 的 `sessionTypesOf`），这种推断出的一对一不算：那样的平台上群员也会被当成唯一的对端。

在场与应答都用这一判定。

## 在场

在场：owner 在这个私聊里最近一次亲手发言起 10 分钟（回审批的消息也算，指令与 WebUI 往这个私聊插话不算）。推到这里的审批等满它的时限，不因 owner 不说话提前结算；它结算时只收回推出带来的延续，owner 自己发言起的 10 分钟已经过了就即刻不在场，没过就到点不在场。不在场时续做要审批，按不在场拒。

做法：

- 在 `inbound:dispatch` 相位认出 owner 时按这个私聊接入审批面（`attend(owner, sink, sessionId)`，每个私聊一份，首次即建），然后照常往下派发。与网关判受众同一时机：IM 私聊的第一条消息与入站同拍建档，判早了可能还没建档。
- owner 亲手发言（派发相位认出的消息，与指令相位截下的回审批的消息）时记下这一刻，并对这个接入上报在场。
- 审批推到这里、送达并带回消息 id 时，对这个接入再上报一次在场，延续到这张结算。推出之后、回执之前 owner 说的话照样算数，回执不覆盖它。
- 推来的审批都结了时，从 owner 最近一次亲手发言起的 10 分钟已经过了就即刻对这个接入上报离开，没过就到那一刻再报；其间 owner 又在这里发言、或又推来审批，就不报。10 分钟与审批服务默认实现的在场窗口一致。

## 推送

审批推到这个接入时，经网关往私聊发一条宿主提示（`source: 'system'`）。不设 `markup`，正文按纯文字发，参数里的 `<at>`、`<image>` 之类逐字显示。文字进本插件字典，网关按会话的语言渲染：

```
需要你批准：exec
命令：rm -rf build
目录：workspace:/proj
引用这条消息回复「同意」，或「拒绝」加原因；5 分钟内不回按过期。
```

事实按审批对象的 `facts` 逐行列出命令、目录、文件、改动、参数，各经 `clipForCard` 清洗并截断：每项最多 500 字，超出的保留首尾各一半、写明省略了多少字。改动疑似含密钥时审批服务不给，这里写「疑似含密钥，不显示内容」。末行的剩余分钟数按审批对象的到期时刻 `expiresAt` 算，不足一分钟的按一分钟；墙钟已过到期时刻、等待的计时器还没到时（系统休眠、改了时钟）也写一分钟。

消息没送达（投递失败、等不到回执或适配器的回执出错）时，owner 在这里看不到它：这张还在等就对这个接入上报离开，没有别的在场审批面时，重连宽限之后按没人在场结算；已经结了的不碰在场。送达、投递结果带了平台消息 id 时，记下这些 id，在场延续到这张结算（见「在场」）。

平台不给消息 id 时审批消息照发，但认不出引用它的回复，随后补一句「这条审批无法在这里应答，请到 WebUI 或终端处理。」

推到私聊的这些消息与别的宿主提示一样记成事件标记进会话历史，不进模型的上下文。

## 应答

在 `inbound:command` 相位截下。owner 的消息同时满足下面两条才处理，其余照常往下（交给指令解析与 agent）：

- 这个私聊接入过，正文是应答词：超过 200 字的不算；去掉首尾的空白（含全角空格）与常见标点（`。！!.~，,？?：:`）后，整条恰为「同意」或「approve」为批准；以「拒绝」或单词「deny」开头为拒绝（「denylist」不算），后面可带原因（作为说明转给模型）。英文不分大小写，不收 y、n。尾部去掉的标点里有问号的是在问，不是应答：「同意？」「同意？！」「拒绝吗？」都不算；「同意吗」「同意不了」「先别批」之类既不是批准也不是拒绝。不是应答的，引用了审批消息也照常往下。
- 引用了这个私聊里的某条审批消息，或这个私聊有推来、还没结的审批。

处理：

- 按入站消息 id 去重：同一条重复到达的静默吞掉。
- 引用的是审批消息：带回审批的内容哈希应答。应答成功不另发，回合本身的回复会说明结果；这张已经结算（含在别处处理过的）回「这张已经处理过。」；其余被拒的（如审批服务不在）回「应答没有生效：」加原因。
- 没引用审批消息：不批，回「要批准或拒绝，请引用那条审批消息回复。」；推着的审批都认不出引用时（平台没给消息 id），回「这条审批无法在这里应答，请到 WebUI 或终端处理。」

处理过的消息一律吞掉：不进指令解析、不交给 agent，也就不会起新的一轮把在跑的那一轮中止。A 结算后紧接推出 B 时，引用 A 的回复只认到 A，回「这张已经处理过」，不会批 B。

照常往下的消息交给 agent。今天的 agent 按会话 latest-wins，新消息到达时中止这个会话里在跑的回合：owner 在私聊里发普通消息（包括引用了审批消息、但不是应答的）时，在等审批的那一轮随之中止，审批按撤销结算。按到达先后处理同一会话的消息由通道层负责，通道层尚未实现，落地后再改。

## 结算

只在过期时往私聊发一行「exec 的审批已过期。」：等满时限的，与覆盖它的在场都失效、宽限内没有恢复的。在私聊里回的、在别处批准或拒绝的、撤销的不另发。

## 已知的边角

- 指令的意图确认（[plugin-commands](./plugin-commands.md)）在等时，会把这个人在这个会话里的下一条消息整条吞掉（y 为确认，其余取消）。两者同时在等、且指令插件的中间件先挂上时，回审批的那条会被当成取消意图确认，审批照旧等着。词表不收 y、n，反过来不会误吞。
- 审批消息经 IM 平台的服务器转发，命令、目录与参数原样在内。
- 记住最近 1000 条审批消息的 id（只记它是哪一张审批的消息）与 1000 条应答过的入站消息 id，更早的认不出。
